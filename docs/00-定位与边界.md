## 1. 定位

**初衷（2026-11-13 重新确认）**

本项目起源于 AEC.Chat 的《切片判定单 V1.0》（`D:\AEC.Chat\AEC.Chat\Law\_src\bailian\切片判定单.md`），并总结 Langchain-Chatchat、HanLP、Chonkie、AnyChunker、Jina Late Chunking、AntSK-FileChunk 六个开源项目而来，目标是发展为**切片规则模板化**。

项目名中的「判定」按判定单原义是**双义**：

- **选型判定（Spec 侧）**：判定该用哪种切法、什么参数 —— 规则模板 `ChunkRuleTemplate`（C-10，0.3.0 已落地）。
- **质检判定（Judge 侧）**：判定切片结果是否合规 —— CCJ-001..017 与 `JudgeReport`（0.2.0 至 0.9.0 持续落地）。

0.2.0 覆盖了 Judge 侧与双库产物，0.3.0 补齐 Spec 侧规则模板与恰长硬切，双判定结构已闭合；剩余缺口为文档类别枚举与用途维度（C-01/C-02）、payload 模板（C-03）。

**首个消费者不定义项目范围（2026-11-14 确认）**

AEC.Chat 是本项目的首个参考消费者，不是服务对象边界。其领域专属需求——规划大纲 payload、时效/效力字段、标题路径、HTTP 宿主集成——由 AEC.Chat 或部署侧在集成层实现，**不因单一消费者而进入核心契约**；除非被证明是跨项目通用需求，才按 rules.md §12 立项。

**目标态（规划，尚不构成对外承诺）**

> 本项目不是一个新的 chunk 算法库，而是一套面向中文专业文档（政府报告、工程报告、项目报告、司法鉴定、合同协议、规范、法规等）的「切片规则模板 + 质检判定 + 双库父子块配套契约」，可对接任意底层切分器（包括 Chatchat、HanLP 等）。一句话：以规则模板判定怎么切，以质检契约判定切得对不对。

**治理口径（2026-11-14 确认）**

本项目的治理对象是**中文专业文档的结构与体裁惯例**：中文句读与条章标记（第X条/第X章/（一）分节）、文书体裁层级（编—章—节—条、篇—章—节、公文要素、鉴定意见书要素），以及「块脱离上下文就读不懂」的承前省略问题（由双库父子块承接）。据此让切分方式可判定、可复现、可回归。

本项目**不判断**内容对错、政策合规、检索效果与策略优劣；这些分别归调用方、Bench 与下游系统。

**现行态（contract v0.9.0 + `impl/csharp`）**

判定「切片结果是否符合契约」，不判定「哪种切片策略更好」（`contract/rules.md` §1）。输入 `DocumentFeature` + `ChunkStrategyOptions` + `RawChunk[]`（可选 `parentChunks` / `pairs`），输出 `JudgeReport`，双库启用时另输出独立 `ParentChildPackage`；关系含 `previousChunkId / nextChunkId / structuralParentChunkId / contextParentChunkId`，旧名 `parentChunkId` 保留为 deprecated 别名（§7.1）。0.3.0 起 Spec 侧落地：`ChunkRuleTemplate` + `/templates/resolve` 做选型判定（§13）；0.8.0 起 `/templates/resolve` 支持模板集（`templates[]`，类别过滤 + 顺序择优，C-18），`ContractChunk` 增可选 `headingPath`（C-17，仅透传保序）。CCJ-015 恰长硬切为第 15 条基础规则，CCJ-016 切片标识唯一为第 16 条，CCJ-017 标识与序号一致性为第 17 条（§8.3、§8.6）。

**两者差距**

目标态中的「payload 模板」在现行契约中仍无定义；「规则模板」（C-10）与「恰长硬切校验」（C-11）已于 0.3.0 落地，「双库」已于 0.2.0 落地。模板中的文档类别枚举（`documentCategories` 目前为自由字符串）依赖 C-01/C-02 收紧。未落地前不得写进对外文案（见 `04-对外文案口径.md`）。

**演进机制（2026-11-14 确认）**

模板不是一次性写死，也不靠模型即兴生成：

1. **运行时**：检索现有模板 → 命中即用；未命中走在线候选（单批生效）→ 不成立则 smart 兜底；每一步都过 Judge。
2. **离线**：同签名样本累计 + 与基线对比 + Bench + 旧样本回归 + 人审 → 晋升为共享模板，反哺下一次检索。
3. 在线候选必须固化为带 `templateHash` 的模板产物，按特征签名缓存，默认只对本批生效。
4. 该机制**只改模板层，不改契约**；契约变更仍按 §12 与 `contract/rules.md` §12.1 执行。详见 `08-模板生产线与自动适配-规划.md`。

## 2. 与外部生态的分工

已有切分库（Langchain-Chatchat、HanLP、Chonkie、AnyChunker、Jina Late Chunking、AntSK-FileChunk）负责「怎么切」，本项目不重复实现切分算法。

| 职责 | 现行 | 规划 |
| --- | --- | --- |
| 切分算法 | 外置插件（`IChunkExecutor`），本仓库不提供 | 不变 |
| 策略选择（分流/选型） | `ChunkRuleTemplate` + `/templates/resolve`（0.3.0 单模板；0.8.0 支持模板集 `templates[]`） | 文档类别枚举收紧（C-01/C-02） |
| 结果校验 | CCJ-001..017（已实现） | 增加条款/段落完整性、表格完整性、碎片过滤等扩展规则 |
| 输出适配 | `ContractChunk` + `JudgeReport` + `ParentChildPackage`（双库，0.2.0 已落地） | payload 模板（C-03）；下游模板托管属范围外（C-09） |
| 建议模板（起步基线） | `templates/recommended/`（**非规范、未评测、不自动加载**，首批 6 类 `rag_retrieval`） | 按 Bench 评测结果由部署方自行演进，仓库只提供起点 |
| 模板生产线（在线候选 / 离线晋升） | 设计见 `docs/08`；生成、证据归档、晋升流程归部署侧工具链 | 不在本仓实现生成器；评测归 Bench；契约只定义合法模板形状 |

## 3. 不做什么（现行生效，引自 rules.md §1.1 与 README 边界约束）

- **不内置文档解析器**：PDF / Word / HTML 版面解析外置，输入只有已解析文本与元信息。
- **不内置切片算法**：`samples/` 也不得交付生产切分算法；Demo 必须 `--plugin` 反射加载外部执行器，未提供则非零码退出、不输出伪造报告。
- **不判定策略优劣**：策略基线由 ChunkJudgeBench 产出并回填。

## 4. 范围外（本仓库不承载）

| 事项 | 说明 |
| --- | --- |
| 文档解析（PDF / Word / HTML） | 外置组件 |
| 切分算法实现 | 外部插件 |
| 向量库写入、检索 / 问答服务 | 下游系统 |
| 下游模板托管（`skill assets`） | 仓库内**不存在**该目录；如需，另立位置，不塞进 `contract/` |
| 文档时效与效力治理（生效、废止、被替代关系） | 归知识库 / 检索 / 编排层；本仓仅原样透传元数据，不做 `validFrom` / `validTo` / `status` 判定与过滤 |
| 切片用途编排（检索 / 生成 / 训练的路由与产物隔离） | 归调用方；本仓可提供 `usagePurpose` 字段与模板，但不做数据集隔离、去重与授权判断 |

## 5. 与 ChunkJudgeBench 的关系

本仓库判定「是否符合契约」；ChunkJudgeBench 在同一契约下横向评测策略优劣，基线由 Bench 产出并回填（rules.md §1、§5.1）。两者共用 `contract/`。

**评测不并入本仓**（2026-11-13 确认）：评测需要语料、检索索引、向量模型与问答回归，与「语言无关契约 + 轻量参考实现」不兼容；阈值由统计方与判定方分离可保证基准独立。Bench 消费本仓的 `ChunkRuleTemplate`（C-10 落地后）跑评测，把 P95 等结果回填为模板参数，本仓只接收数值、不参与产生数值。

## 6. 变更纪律

1. **契约变更**：在 `contract/` 内按 rules.md §12 顺序执行（rules.md → schema → openapi → impl + 测试）。
2. **规划变更**：改本目录对应文档；台账编号（C-xx）只增不改、不复用。
3. **对外文案**：仅在 `04-对外文案口径.md` 中标为「可发布」的条目才可对外使用。
