# 18 实现符合性复查（2026-11-14）

- **前提**：按要求把 `contract/` 原文视为正确，只查实现有没有照契约本意执行；不评价契约本身。
- **范围**：`impl/csharp` 全部非生成源码（11 个 `.cs`，约 2400 行）+ 6 项运行探针 + 74 项既有测试。
- **结论**：17 条基础规则的**编号、级别、作用域 17/17 对齐**；**条件与判定口径 7 条完全一致、10 条存在偏差或口径差**。出现"契约要求不通过、实现放行"的实证共 2 处：C1（`targetSize` 越界）成因是规则表无载体，按 §7 归契约缺口；C3（`CCJ-015` 页码容错）属实现自身偏差 I-02，可直接修。另有 I-01 属"判定器改写输入"，不是放行问题但更伤判定诚信。
- 未修改任何仓库文件；探针工程在 agent workspace，不在仓库内。

## 1. 方法

1. 通读 `ChunkRuleEngine.cs`（17 条规则中的 001-007、014-017）、`ParentChildRules.cs`（008-013）、`HardCutRule.cs`（015）、`ChunkJudgeService.cs`、`TemplateResolver.cs`、`ChunkRelationBuilder.cs`、`ChunkValidator.cs`、三个模型文件。
2. 对"读代码推不出结论"的 6 处，用 `ChunkJudgeService` / `ChunkValidator` / `ChunkRelationBuilder` / `TemplateResolver` 实际调用（仓库外探针），取运行结果而非推断。
3. 用 `dotnet test` 确认基线 74/74 通过，并检查这 6 个场景是否有对应用例。

## 3. 可修的实现偏差（不改契约即可修）

| 编号 | 偏差 | 契约原文 | 证据 | 后果 | 修法 |
| --- | --- | --- | --- | --- | --- |
| I-01 | 结构父被覆盖 | §7.1 L207「调用方已显式指定时保留原值，不覆盖」 | `ChunkRelationBuilder.cs` L24-34、L43-51：两字段冲突时取 `parentChunkId`，并把 `structuralParentChunkId` 改成同值 | **CCJ-014 经 `Judge`/`JudgeContractChunks` 恒不触发**（两值被强制相等）；调用方给的结构父被静默改写 | 改为"仅两值为空时才推断"；冲突时各保留原值，交 CCJ-014 报 |
| I-02 | `CCJ-015` 页码容错比契约宽 | §8.5 L308「句读 + 可选空白 + 1..4 位纯数字」 | `HardCutRule.cs` L17-19：`[句读][闭合符]?\s*\d{1,4}$`，多允许一个闭合符 | 结尾形如 `。】123` 的恰长切片**放行**（契约应判 error） | 正则改为 `[句读]\s*\d{1,4}$` |
| I-03 | `CCJ-003` 的 `detail.charCount` 写死 "0" | §9.2 `detail` 为机读字段，须与事实一致 | `ChunkRuleEngine.cs` L180 | 全空白切片（如 3 个空格）报告 `charCount=0`，与实际码位数矛盾 | 改 `ChunkTextMetrics.CountCharacters(chunk.Text)` |
| I-04 | `traits` 封闭枚举未校验 | §13.1 L426「`traits` 封闭枚举……扩枚举走次版本」 | `TemplateResolver.ValidateRule` 只校验 `chunkMode`/`pattern`/`chunkSize`，不校验 `traits` | 库 API 接受任何 trait 字符串；模板写错字不会被发现（Schema 能拦，库 API 不能） | `ValidateTemplate` 校验 `appliesTo.traits` 与 `decision.rules[].traits` 均属五个枚举值 |
| I-05 | `CCJ-008` 少一条契约条件 | §8.3 L284 条件含"子块 ID 重复" | `ParentChildRules.cs` L188-298 无全局子块 `chunkId` 重复检查 | 同一重复由 CCJ-016 报 error，判定结论不变，但规则归属与契约不符；`appliedRules`/`issues` 追溯对不上 | CCJ-008 增子块 `chunkId` 重复检测（与 CCJ-016 双报，契约两条条件都写了） |
| I-06 | `/rules` 在库侧无实现载体 | openapi `GET /rules` → `RuleManifest{contractVersion, rules[]}` | 全仓仅 `ContractConstants.ContractVersion` 一处，**无 `RuleManifest` 类型、无组装方法** | 即便将来有宿主，该端点也无实现可挂 | 增 `BuildRuleManifest()`：`contractVersion` + `RuleEngine.Rules` 映射为 `RuleDescriptor` |

## 4. 口径差异（结论一致，但与契约字面不同）

| 编号 | 差异 | 说明 |
| --- | --- | --- |
| W-01 | `CCJ-004`/`CCJ-009` 用 `text` 计算值，而非字段 `charCount` | 契约条件写 `charCount > ...`。字段与正文不符时，契约字面会多报一条长度问题，实现只报 CCJ-017。**结论都是不通过**，差别在报告内容 |
| W-02 | `CCJ-001` 同时检查 `document.metadata` | §8.3 只说"Metadata 五字段任一缺失或为空"，未限定对象；实现把文档与切片一起查，`chunkId` 为 null 的文档级 issue 是契约未明说的形态 |
| W-03 | `CCJ-001` 的"缺失"分支在服务路径不可达 | 模型用 `required`，Schema 也 required；缺少字段的实例在反序列化阶段即失败（400），能进判定的只有"空值"。契约"缺失或为空"两条分支，实际只有一条活着 |
| W-04 | `CCJ-017` 对重复 `index` 同时报"重复"与"序号不连续" | §8.6 说"重复与缺号分别报告"，未说同一重复是否可再报一条连续性汇总 |
| W-05 | `CCJ-002` 按 `strategy` 去重，同一非法策略只报一次 | 契约"报告非法策略名"未要求逐块；与 CCJ-001"逐字段报告，含命中处数"的写法不一致 |
| W-06 | `JudgeWithExecutor` 允许省略 `options`，默认 `TargetSize=600` | 契约 `ExecuteRequest` 把 `options` 列为必填；库 API 比契约宽，会产出契约外的默认策略 |
| W-07 | `previousChunkId`/`nextChunkId` 无条件按 `index` 重算 | 契约只写"按 index 顺序的前一个/后一个"，没写"不覆盖"（该句在结构父段落）。输入里的错误指针因此永远不被判——但契约也没有对应规则 |
| W-08 | `CCJ-010` 多判"父块偏移越界/长度非正" | §7.2 要求父块 `text` 为原文精确子串，偏移非法时该条件本就不成立，故**判定结论与契约本意一致**；差异仅在于 §8.3 未枚举这个理由（`detail.reason=range`） |

## 7. 契约正文有要求、但规则表没有载体（**不算实现违约**）

这四项无论实现怎么写，都无法在不改契约的前提下报出问题——判定器只能输出 CCJ 编号，规则表里没有对应编号就无法承载：

| 契约要求 | 位置 | 现状 |
| --- | --- | --- |
| `targetSize` 取值 1..1500 | §5.1 L120 | CCJ-002 只查正则（无上限）、CCJ-007 只查 `options`；C1 实证 `structure@2000` 经契约切片路径全过 |
| `maxChunkSize` 是"单块硬上限" | §5.2 L132 | §8.3 只有 CCJ-004（固定 1500），无规则比较切片与 `maxChunkSize` |
| 切片元信息"与文档一致" | §4.1 L95 | CCJ-001 只查非空，无等值比较 |
| 父块 `index` 从 0 起连续、`charCount` 正确、落在结构单元边界 | §7.2 L216/L222/L228 | CCJ-017 明示只作用子块；无父块规则；Schema 也不校验连续性与边界为 true |

按 `docs/14` 的编号，这四项就是 K-03、K-04、K-05、K-11。**本轮不把它们改判为"实现 bug"**：结论仍是"契约需补规则"，补完后实现才可能照做。

## 8. 测试覆盖情况

- `dotnet test` 74/74 通过（2026-11-14 实测）。
- 6 个探针场景中，只有 CCJ-014 有单元测试（`ParentChildRulesTests.cs` L57-65），且是**直接调 `ChunkValidator`**，不经 `Judge`/`JudgeContractChunks`——正好绕开了 I-01 的覆盖路径。
- C1、C3、C5 无任何用例；C4、C6 无断言覆盖。**所以 74 项全绿并不代表这些契约要求已被守住。**

## 9. 建议修复顺序（全部不改契约）

1. I-01（结构父不覆盖 + 让 CCJ-014 可达）——影响判定器诚信，优先。
2. I-02（`CCJ-015` 页码容错收窄）、I-05（`CCJ-008` 补条件）——影响判定结论。
3. I-04（trait 枚举校验）、I-06（`/rules` 载体）——影响契约能力完整性。
4. I-03（`detail` 失真）——报告质量。
5. 每修一条，补一条"应触发/不应触发"双向用例；把 §2 的 6 个探针转成正式测试，避免再出现"无覆盖即绿"。
