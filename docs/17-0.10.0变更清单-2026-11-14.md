## 1. 四项规则级别：建议与理由

| 编号 | 建议级别 | 理由（与本契约既有级别对齐） | 若不判定的后果 |
| --- | --- | --- | --- |
| K-03 | **error** | 策略名是切片身份的前缀（CCJ-017 的 `{strategy}#{index}` 直接依赖它）；与 CCJ-002（策略名非法，error）同族，同类问题不应跨级别 | `structure@2000#0` 全链无拦；`targetSize` 与 `options` 不一致时 CCJ-015 的"恰长"基准错位，判定结论不可信 |
| K-04 | **warning** | 长度类问题在契约中统一为 warning（CCJ-004 超 1500、CCJ-009 父块超阈值）；"超 `maxChunkSize`"不破坏可解析性，只影响切分质量 | `targetSize=1200, maxChunkSize=600` 时 1100 字切片静默通过，"硬上限"是空话 |
| K-05 | **error** | 元信息错配是**数据错配**（切片回指错文档），不是质量偏好；与 CCJ-001（元信息缺失，error）同族 | 错 `title`/错 `createTime` 的切片判通过，下游按切片元信息归档会张冠李戴 |
| K-11 | **error** | 父块 `index`/`charCount` 是 CCJ-009、CCJ-017 复算的基础数据；与 CCJ-017（标识/序号/计数不一致，error）同族 | 父块 `charCount` 错值让 CCJ-009 误判、漏判；父块缺号/重复无法发现 |

**级别取舍的边界（避免把配置错升级成数据错）**：K-04 不宜定 error。`maxChunkSize < targetSize` 本身已由 CCJ-007 报 error；若 K-04 也定 error，同一份"配置写错"的输入会同时产出配置错误与数据不合格两类红，责任面被放大。warning 与契约既有长度语义一致。

## 2. 新增基础规则（建议编号 CCJ-018..CCJ-021）

| 新编号 | 级别 | 触发条件 | 输出要点 | 对应缺陷 |
| --- | --- | --- | --- | --- |
| CCJ-018 | error | 子块 `strategy` 的 `{type}` ≠ `options.strategyType`；或 `{targetSize}` ∉ 1..1500；或 ≠ `options.targetSize` | 报告期望值与实际值 | K-03 |
| CCJ-019 | warning | `options.maxChunkSize < 1500` **且** `charCount > options.maxChunkSize` **且** `charCount <= 1500`（`charCount > 1500` 由 CCJ-004 独占；`maxChunkSize = 1500` 时本规则不触发） | 报告实际字符数与配置阈值 | K-04 |
| CCJ-020 | error | 子块或父块 `metadata` 五字段与 `document.metadata` 不等（`createTime` 按 ISO 8601 解析后比较时刻，解析失败按逐字比较） | 逐字段报告差异 | K-05 |
| CCJ-021 | error | 父块 `index` 非 `0..N-1` 连续（含重复/缺号）；`charCount` ≠ `text` 码位数；`startOffset`/`endOffset` 越界或 `endOffset <= startOffset` | 报告字段、期望值与实际值 | K-11、K-21 |

两条结构性要求：

1. **只新增编号，不动老规则**。§8.4 禁止改 CCJ-001..017 的判定条件与级别，所以 K-05 不能"给 CCJ-001 加等值比较"，K-21 不能"给 CCJ-010 加偏移判定"——都只能新增。
2. **CCJ-021 收编 K-21**。参考实现现在在 CCJ-010 里多判"父块偏移越界/长度非正"（契约正文没写），落地时把这部分移到 CCJ-021，CCJ-010 回归契约原文（重叠 / 非精确子串 / 拼接不等价三项）。

配套三条细则（自查后补，缺了会产生重复报错或双计）：

- **CCJ-018 前置**：仅在 `strategy` 通过 CCJ-002（正则匹配成功）后才执行；策略名整体非法时只报 CCJ-002，避免同一块报两条。
- **CCJ-019 排除区**：条件里必须带 `charCount <= 1500`。否则 `maxChunkSize=1200`、切片 1600 字时会同时触发 CCJ-004 与本规则，一处缺陷计两次（初稿漏了这条）。
- **CCJ-005 作用域已核实**：`OffsetConsistencyRule.Evaluate` 只遍历 `context.Chunks`（子块，`ChunkRuleEngine.cs` L241），不碰父块；因此 CCJ-021 的"父块偏移"与 CCJ-005 无重叠，不存在双计。

**K-03 的 Schema 侧（初稿漏写，自查补上）**：`strategy` 的区间**可以在 Schema 层穷举**，不必只靠规则。实测 `^(?:[a-z][a-z0-9_-]*)@([1-9]|[1-9][0-9]|[1-9][0-9][0-9]|1[0-4][0-9][0-9]|1500)$` 对 `structure@600`/`structure@1500` 通过，对 `structure@1501`/`structure@2000`/`structure@0600` 拒绝。落地时需同步收紧 3 个文件里的 5 处 pattern（`contract-chunk.json` L22 的 `chunkId`、L43 的 `strategy`；`judge-report.json` L30；`parent-child-package.json` L16、L72）。规则（CCJ-018）与 Schema 两层都要，缺任一层都会漏：Schema 管消费物，规则管 `JudgeReport` 里的可报告性。

## 3. 七项 MINOR 的改法

（B 批 12 项 = 4 条新规则（§2）+ 本节 7 项 + K-13（改判 PATCH，见 §4））

### K-06 `regex` 的条件约束与 `pattern` 回填落点

- `chunk-rule-template.json` 的 `$defs/decisionRule` 增 `if/then/else`：`chunkMode=regex` → `required: [pattern]` 且 `minLength 1`；其余模式 → 显式禁止 `pattern`（用 `"not": {"required": ["pattern"]}`，不能只靠 `additionalProperties:false`，因为 `pattern` 是已声明字段）。
- **不新增 `chunk-strategy-options.pattern`**（初稿曾建议加，自查后撤回）：`pattern` 的单一来源保持为模板与选型响应（`TemplateDecision.pattern` 已存在）。再往 options 加一份就是第三处定义，与 §7.2 记的"引用单一来源"做法相反；执行器要用 `pattern` 时由宿主从选型响应取，不经 options 回填。
- `rules.md` §13.3 增一句"决策结果中的 `pattern` 不回填 `options`"；§13.2 把"`regex` 时 `pattern` 必填"从散文降级为"由 Schema 约束"。

### K-07 `template` / `templates` 恰好一个

- 实现已有 400 校验，落地改为以 Schema 同构的判定（两都提供/都不提供 → 400），并补 2 项 HTTP 级或服务级测试。

### K-08 错误码登记表（413 与资源边界本期不做）

- `ErrorResponse.error.code` 从 `examples` 改为 `enum`，**只登记已有语义的 5 码**：

| 码 | HTTP | 场景 |
| --- | --- | --- |
| `invalid_request` | 400 | 请求体结构/必填缺失 |
| `invalid_options` | 400 | 选项非法（CCJ-007 同源，保留现有示例值） |
| `invalid_chunk` | 400 | 切片结构不合法、无法进入判定 |
| `no_applicable_template` | 400 | 类别过滤后无候选（§13.3 已有此码） |
| `executor_not_registered` | 404 | `/judge/execute` 未注册执行器 |

- **413 与资源边界（1 MiB / 10000 切片 / 1,000,000 码位）本期不写进契约**（初稿写了，自查后撤回）。理由：K-28 表明仓库没有 HTTP 宿主，任何新增的 413 与上限数值在 0.10.0 都**无法执行、无法验证**，写进去只是重犯本报告一直在批的"契约写了约束却没判定"。待宿主落地时与 K-28 一并定义，届时走独立 MINOR。

## 4. K-13 建议改判（与 `docs/14` 不同，需你点头）

**原建议**（`docs/14`）：`MINOR`，规范化响应改 `{chunks, parentChunks?, pairs?}`。

**改判理由**：

1. `/chunks/normalize` 的 `200` 响应现在是**裸数组**（`openapi.yaml` L52-54）。要回显父块必须把数组改成对象——这是**改变既有响应形态**，消费方全部要改；按 §12.1 属比 MINOR 更重的动作，收益却不成立。
2. 父块的 `ContextParentChunk` 本身就是契约切片形态，归一化对它无事可做；回显只是"把入参原样再吐一遍"。
3. 真正的问题不是"没回显"，而是"`parentChunks`/`pairs` 在 normalize 里到底算什么"没有定义。

**改判建议**：降为 `PATCH` 文本澄清 + 实现侧补校验：

- `rules.md` §3/§7 增一句：normalize 只做 `RawChunk → ContractChunk` 归一化，**不判定**，`CCJ-013` 不适用于本端点；
- `parentChild.enabled=false` 且请求携带 `parentChunks`/`pairs` → **400 `invalid_request`**（由宿主校验，不产出 `JudgeReport`），与 CCJ-013 的语义保持一致；
- 响应形态不动。
