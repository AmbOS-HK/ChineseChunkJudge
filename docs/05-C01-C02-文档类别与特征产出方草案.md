# C-01 / C-02 草案：文档类别枚举与特征产出方

> 状态：**草案，未冻结**。本文件不改 `contract/` 与 `schema/`；待拍板后按 §12 变更流程落地。
> 关联：C-01（`documentCategory` 枚举）、C-02（`traits` 由谁产出）。台账见 `docs/02-契约演进.md`。
> 范围声明：文中的文档示例仅用于说明类别边界，**不构成项目服务范围**。AEC.Chat 是首个参考消费者，其领域需求不自动进入核心契约（见 `docs/00` §1）。

## 1. 目的与范围

- 本仓（ChineseChunkJudge）承担**选型判定（Spec）**与**质检判定（Judge）**，不承担文档解析、NLP 推断与向量化。
- `documentCategory` 与 `traits` 是**调用方输入**，本仓只消费，不生成、不猜测、不补全。
- 二者作用不同：`documentCategory` 用于**选模板 / 评测分组 / 报表口径**；`traits` 用于**模板内有序规则匹配**。

## 2. 决策项 A：`documentCategory` 封闭枚举（14 类模板族）

`documentCategory` 在本草案中不是“图书分类”，而是**模板族**：同一取值意味着“同一主导检索单元 + 同一主导切分策略”，不意味着“同一种公文文种”。名称只是稳定句柄，允许体裁名与形态名混用，但每类的定义、检索单元、主导切分必须写死。

枚举声明顺序即**报表与模板展示的默认顺序**，不用于归属裁决；归属裁决见下方判定树。

| 展示序 | 枚举值 | 主导检索单元 | 定义 / 典型语料 | 主导切分 | 不属于本类的情形 |
| --- | --- | --- | --- | --- | --- |
| P1 | `government_report` | 章节 | 政府机关（含承担行政职能的事业单位）出具的履职、专题、调研、督查报告 | 标题层级 | 规划、工程报告、鉴定/评估报告 |
| P2 | `engineering_project_document` | 章节 / 表 | 工程项目全周期文件：可研、施组、监理、竣工、项目后评价 | 标题层级 + 表格保护 | 政府规划、单份鉴定意见、施工合同 |
| P3 | `government_plan` | 章节 | 政府规划纲要与专项规划：五年规划、国土空间规划、产业专项规划 | 标题层级 + 父块 | 工作报告、项目建议书、可研报告 |
| P4 | `law_regulation` | 条 | 法律、司法解释、部门规章、地方规范性文件 | 条章正则 | 技术标准、内部制度、诉讼文书 |
| P5 | `technical_standard` | 条 / 节 | 国标、行标、CNAS、CMA、司法鉴定技术规范 | 条章 + 分节 | 法律法规、内部制度、操作手册 |
| P6 | `internal_policy` | 条 | 企业/机构内部制度、办法、细则、流程 | 条章正则 | 对外公文、合同、操作手册 |
| P7 | `contract` | 条 | 合同、协议、委托书、约定条款 | 条款正则 | 单方报告、内部制度、对外公文 |
| P8 | `litigation_document` | 份 / 案 | 起诉书、判决书、裁定书、调解书、代理词、答辩状、庭审笔录、执行文书 | 要素保留 + 智能切分 | 鉴定/评估报告、合同、法律法规 |
| P9 | `appraisal_report` | 结论段 | 鉴定意见书、检验检测报告、审计报告、评估报告 | 固定要素 + 段切分 | 政府工作报告、工程过程报告、诉讼文书 |
| P10 | `official_document` | 份 | 通知、请示、批复、函、意见、决定、决议、通报、公告、通告、议案、命令、公报、会议纪要 | 短文书整体优先 | 报告、规划、内部制度 |
| P11 | `manual` | 步骤 | 操作手册、作业指导书、培训讲义 | 步骤边界 | 内部制度、强制性标准原文 |
| P12 | `tabular_record` | 整表 / 行组 | 清单、台账、名册、标准表格 | 表格保护，禁止拦腰切 | 报告、手册、合同中的附表 |
| P13 | `qa_pair` | 一问一答 | FAQ、客服问答、访谈对话 | 问答对为最小单元 | 手册中偶发的问答段落 |
| P14 | `other` | 兜底 | 新闻、网页、邮件、专利、病历、招投标文件、企业非项目工作报告、杂项 | smart fallback | 不得作为缺省兜底值 |

**唯一归属判定树**（按顺序判断，命中即停止）：

1. 主体是整表 / 行组，检索目标是“表” → `tabular_record`
2. 主体是一问一答，检索目标是“问答对” → `qa_pair`
3. 产生法律规范效力 → `law_regulation`
4. 产生技术规范效力 → `technical_standard`
5. 形成双方/多方权利义务 → `contract`
6. 属于诉讼、审判、执行程序 → `litigation_document`
7. 以鉴定/检验/审计/评估结论为主体 → `appraisal_report`
8. 文件本身是政府规划/纲要/专项计划 → `government_plan`
9. 政府机关就自身履职、专项、调研、督查形成的报告 → `government_report`
10. 工程项目全周期文件 → `engineering_project_document`
11. 按公文格式对外行文，且不是报告或规划 → `official_document`
12. 只在本单位内部生效的制度/办法/细则/流程 → `internal_policy`
13. 以操作步骤/参数/图示为主 → `manual`
14. 以上均不命中 → `other`

约束建议：

1. **主单元优先**：一份文档同时含章节、表格、问答时，按“用户主要要拿回什么”定类，不按字符占比最大的形态定类。报告、手册、合同里的附表仍归原类，不因出现表格改判 `tabular_record`。
2. **问答优先**：整份文档以问答对组织才归 `qa_pair`；手册里的 FAQ 附录、报告里的访谈摘录仍归原类。
3. 命名固定小写 snake_case。允许用体裁名（`government_report`）或形态名（`tabular_record`）作句柄，但不得再新增“发布主体 + 领域”的复合名；`judicial_document` 因“司法包含司法鉴定”歧义，本方案统一改为 `litigation_document`。
4. 0.x 阶段**只增不删**；新增取值走 `MINOR`，删除或改名走 `MAJOR`；仅调整展示顺序走 `PATCH`。**数量不是规范不变量**，本期为 14 个。
5. `other` 是**显式声明**，不是缺省值；调用方拿不准时必须自己判断，不允许“不填就 other”。
6. 同一文档只能落一个主类；如需表达“报告里有很多表”，用 `traits.dense_table`，不得双标类别。
7. 边界规则（按顺序适用）：
   - `tabular_record` vs 任一文体类：表是主体、检索单元是整表/行组才归表类；附表不算。
   - `qa_pair` vs `manual` / `other`：全文以问答对组织才归问答类。
   - `law_regulation` vs `technical_standard`：法律规范 vs 技术规范；强制性标准仍归 `technical_standard`。
   - `law_regulation` vs `internal_policy`：对外产生法律效力 vs 只在单位内部生效。
   - `internal_policy` vs `official_document`：对内生效 vs 对外行文。
   - `contract` vs `official_document`：产生双方/多方权利义务 vs 单方行文。
   - `litigation_document` vs `appraisal_report`：诉讼/审判/执行程序 vs 鉴定/检验/审计/评估结论。
   - `appraisal_report` vs `government_report` / `engineering_project_document`：对某对象的结论 vs 政府自身履职过程 / 工程项目过程。
   - `government_report` vs `engineering_project_document`：政府自身工作 vs 具体项目全周期；以具体项目为对象的报告归 `engineering_project_document`。
   - `government_plan` vs `engineering_project_document`：区域/组织未来安排 vs 具体项目前期文件；项目建议书、可研归 `engineering_project_document`。
   - `technical_standard` vs `manual`：要求/准则 vs 操作步骤/参数。
   - `manual` vs `internal_policy`：操作指导 vs 规则文本（应当/不得/责任）。

**与 12 类草案的迁移**（仅文档层，尚未进契约）：

| 14 类 | 来源（12 类 / 旧名） |
| --- | --- |
| `government_report` | `work_report` / 旧 `government_report` |
| `engineering_project_document` | `project_report` / 旧 `engineering_project_report` |
| `government_plan` | `development_plan` / 旧 `government_plan` |
| `law_regulation` | `regulation` / 旧 `law_regulation` |
| `technical_standard` | `standard` / 旧 `technical_standard` |

## 2.1 14 类的验证状态

- **结构效度已完成**：逐类检查检索单元是否唯一、模板签名是否可区分、命名是否可判定，结果见 `docs/11-14类模板族规范性与科学性验证-2026-11-14.md`。
- **条件通过项**：`law_regulation` / `technical_standard` / `internal_policy` / `contract` 四类都以“条”为主单元，模板粒度是否该合并，需用 Bench A/B 证明差异；当前保留四类，理由是条章正则与文档级结构不同，但这是**待验证假设**，不是已证结论。
- **命名修正项**：`judicial_document` → `litigation_document`。
- **实证效度未完成**：尚无标注语料、双人标注一致性、Bench 模板 A/B；因此本方案是“**结构上可用、尚未实证最优**”的草案，不是已冻结的规范枚举。
- **已知内容缺口**：非政府机关的企业履职报告目前只能落 `other`；冻结前先统计该类语料占比，再决定是否改为 `work_report` 或新增 `enterprise_report`。
- **冻结门槛**：每类 ≥30 份标注文档；双人标注 Cohen's kappa ≥0.70；Bench 上按类模板不劣于强制 smart fallback；三项同时满足才建议冻结。

## 3. 决策项 B：特征产出方与职责边界

| 角色 | 职责 | 不做的事 |
| --- | --- | --- |
| 调用方 / 执行器（AEC.Chat 等） | 文档解析、结构识别、产出 `documentCategory` 与 `traits[]` | 不实现判定规则 |
| 本仓 Spec（`TemplateResolver`） | 消费 `traits` 与类别，按模板决策表选型；不解析文档 | 不产出特征、不补全缺失特征 |
| 本仓 Judge | 校验切片结果并出 `JudgeReport` | 不做选型、不解析文档、不做 NLP/LLM 推断 |
| 本仓 Bench（独立仓） | 用同一模板与契约做策略评测、回填分位数 | 不产出判定结论 |

约束建议：

1. `traits` 为封闭枚举，沿用现行 5 个：`article_numbering`、`section_numbering`、`weak_structure`、`dense_table`、`pdf_no_structure`；扩枚举走 `MINOR`。
2. 执行器**无法识别**某个特征时，必须在数组中**省略**该 trait，不得猜测、不得伪造。
3. `traits` 全为空数组是合法输入，语义为「未识别到任何结构特征」，由模板 fallback 兜底。
4. 本仓不因类别或特征缺失而自行推断；如需推断能力，只能放在执行器或旁路服务，不进本仓。

### 3.1 特征契约（建议冻结口径）

本仓规范的是**特征的词汇表与语义**，不是识别方法。

| 项 | 建议 | 说明 |
| --- | --- | --- |
| `traits` 取值 | 封闭 5 值，沿用现行 | 扩枚举走 `MINOR` |
| `traits` 空数组 | 合法 | 表示「未声明结构特征」，不等于「未知」，不触发报错，由 fallback 兜底 |
| `traits` 无法识别某项 | 省略该值 | 不得猜测、不得伪造 |
| `documentCategory` 取值 | 封闭枚举，按 C-01 冻结 | 枚举外值一律拒绝，不做最接近匹配 |
| 选型请求中的类别 | **必填且非空** | 空数组视为未提供类别，拒绝，不得静默走 fallback |
| `traits` 与 `structureHints` | 互不校验 | `traits` 是产出方结论，`structureHints` 是原始提示；不一致不报错，Judge 不据此推断 |
| 传递位置 | 本期仍只在 `/templates/resolve` 请求 | `DocumentFeature` 目前无 `documentCategory` / `traits`；是否随文档全程流转见 §5 第 6 问 |

错误处理建议（与现行 OpenAPI 对齐，统一用 `400`，不新增 `422`）：

| 情形 | 处理 |
| --- | --- |
| `documentCategories` 为空数组 | `400`，错误码建议 `document_category_required` |
| `documentCategories` 含枚举外值 | `400`，错误码建议 `document_category_unknown`，并列出合法枚举 |
| `traits` 含枚举外值 | `400`，错误码建议 `trait_unknown` |
| `traits` 为空 | 合法，继续选型 |

> 原草案写 `422`，与现行 `contract/openapi.yaml` 只有 `400` 的事实不一致，故改为 `400`；若坚持 `422`，属新增响应码，需单独走契约变更。

## 4. 决策项 C：未命中处理

分三种情形，互不替代：

| 情形 | 建议处理 | 理由 |
| --- | --- | --- |
| `documentCategories` 为空数组 | 宿主返回 `400`，错误码 `document_category_required` | 类别决定模板选择与报表口径，静默补值会污染评测分组 |
| `documentCategories` 为枚举外字符串 | 宿主返回 `400`，错误码 `document_category_unknown`，列出合法枚举 | 契约外值属于调用方错误，不能由本仓猜测最接近类别 |
| `traits` 含枚举外值 | 宿主返回 `400`，错误码 `trait_unknown` | `traits` 是封闭枚举，扩值只能走契约变更 |
| `traits` 未命中任何 `decision.rules` | **强制 smart fallback**（现行已实现） | 判定单原始口径：不允许无决策结果；兜底必须可执行、可复现 |
| `documentCategories` 与 `appliesTo` 无交集 | **模板集形态返回 `400` `no_applicable_template`**；单模板形态仍由部署侧选定 | 0.8.0（C-18）起 `TemplateResolver` 已按 `appliesTo` 做类别过滤，旧描述已过时 |

需要明确的一点：`documentCategory` 必填与 `traits` 兜底是**两条独立防线**。前者保证输入合法，后者保证有决策结果；不能用 fallback 掩盖类别缺失或类别非法。

## 5. 待拍板的问题

1. 类别枚举按 §2 的 **14 类模板族**冻结，还是继续保留 12 类“文书功能”方案？迁移表已列在 §2。
2. `documentCategory` 是否设为**必填**（空数组或枚举外值返回 `400`），还是允许缺省？
3. 特征产出方是否确认**只在调用方/执行器**，本仓完全不推断？
4. `official_document` 是否接受「党政机关与企业公文共用一类」，还是必须按主体再拆？
5. `usagePurpose` 三维度（检索 / 生成 / 训练）是否作为独立字段新增？若新增，是必填还是可选（缺省 `rag_retrieval`）？
6. 特征是否需要在 `DocumentFeature` 中承载，随 Normalize / Judge 全程流转并为报告提供回溯？建议**本期不做**，另立项处理；若做，新增可选字段走 `MINOR`。
