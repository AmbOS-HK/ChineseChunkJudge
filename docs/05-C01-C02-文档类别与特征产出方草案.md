# C-01 / C-02 草案：文档类别枚举与特征产出方

> 状态：**草案，未冻结**。本文件不改 `contract/` 与 `schema/`；待拍板后按 §12 变更流程落地。
> 关联：C-01（`documentCategory` 枚举）、C-02（`traits` 由谁产出）。台账见 `docs/02-契约演进.md`。
> 范围声明：文中的文档示例仅用于说明类别边界，**不构成项目服务范围**。AEC.Chat 是首个参考消费者，其领域需求不自动进入核心契约（见 `docs/00` §1）。

## 1. 目的与范围

- 本仓（ChineseChunkJudge）承担**选型判定（Spec）**与**质检判定（Judge）**，不承担文档解析、NLP 推断与向量化。
- `documentCategory` 与 `traits` 是**调用方输入**，本仓只消费，不生成、不猜测、不补全。
- 二者作用不同：`documentCategory` 用于**选模板 / 评测分组 / 报表口径**；`traits` 用于**模板内有序规则匹配**。

## 2. 决策项 A：`documentCategory` 封闭枚举

枚举声明顺序即**报表与模板展示的默认顺序**，不用于归属裁决；归属裁决见下方判定树。

**划分原则**：一级轴是**文书功能**，二级只在「报告」分支按**对象**细分（work / project / assessment）。发布主体、项目阶段、法律效力只作为判定线索，不作为与功能并列的分类轴。版式差异（表格密度、是否扫描件）继续由 `traits` 承载，不进类别。

| 展示序 | 枚举值 | 定义 | 典型文档 | 不属于本类的情形 |
| --- | --- | --- | --- | --- |
| P1 | `work_report` | 机关、事业单位、企业就履职、专项工作、调研、督查形成的报告 | 政府工作报告、专项工作报告、督查报告、调研报告、企业年度工作报告 | 规划、项目报告、评估/鉴定报告 |
| P2 | `project_report` | 工程项目全周期形成的报告与阶段文件 | 项目建议书、可行性研究报告、施工组织设计、监理月报、竣工验收报告、项目后评价 | 规划纲要、评估报告、施工合同 |
| P3 | `development_plan` | 面向未来的规划、纲要、专项计划 | 国民经济和社会发展五年规划纲要、国土空间规划、产业专项规划、企业发展规划 | 工作报告、项目建议书、可研报告 |
| P4 | `official_correspondence` | 按公文格式对外行文的其他文种（不含报告、规划） | 通知、请示、批复、函、意见、决定、决议、通报、公告、通告、议案、命令、公报、会议纪要 | 报告、规划、内部制度 |
| P5 | `litigation_document` | 诉讼、审判、执行程序文书 | 起诉书、判决书、裁定书、调解书、代理词、答辩状、庭审笔录、执行文书 | 鉴定/评估报告、合同、法律法规 |
| P6 | `regulation` | 法律法规、司法解释、部门规章、地方规范性文件 | 《民法典》《民事诉讼法》司法解释、司法部规章 | 技术标准、内部制度、诉讼文书 |
| P7 | `standard` | 技术标准、认证准则、检验规程 | CNAS-CL01、CMA 评审准则、司法鉴定技术规范 | 法律法规、内部制度、操作手册 |
| P8 | `internal_policy` | 企业/机构内部制度、办法、细则、流程 | 内部管理办法、实施细则、审批流程、岗位规范 | 对外公文、操作手册、合同 |
| P9 | `operational_manual` | 操作手册、作业指导书、培训教材 | 鉴定操作手册、设备作业指导书、培训讲义 | 内部制度、强制性标准原文 |
| P10 | `contract` | 合同、协议、委托书、约定条款 | 司法鉴定委托合同、服务协议 | 单方报告、内部制度、对外公文 |
| P11 | `assessment_report` | 非政府履职、非工程项目、非诉讼程序的鉴定/检验/审计/评估/研究结论文书 | 鉴定意见书、检验检测报告、审计报告、评估报告、研究报告 | 政府工作报告、工程报告、诉讼文书 |
| P12 | `other` | 明确不属于以上十一类的文档 | 新闻稿、书信邮件、专利文书、病历、招投标文件、纯台账表格 | 不得作为缺省兜底值 |

**唯一归属判定树**（按顺序判断，命中即停止）：

1. 产生法律规范效力 → `regulation`
2. 产生技术规范效力 → `standard`
3. 形成双方/多方权利义务 → `contract`
4. 属于诉讼、审判、执行程序 → `litigation_document`
5. 按公文格式对外行文，且不是报告或规划 → `official_correspondence`
6. 面向未来的规划/纲要/专项计划 → `development_plan`
7. 属于报告：按对象分 `work_report`（履职/专项/调研/督查）、`project_report`（工程项目全周期）、`assessment_report`（鉴定/检验/审计/评估/研究结论）
8. 只在本单位内部生效的制度/办法/细则/流程 → `internal_policy`
9. 以操作步骤/参数/图示为主 → `operational_manual`
10. 以上均不命中 → `other`

约束建议：

1. 命名固定小写 snake_case；名称只表达「功能 + 对象」，不写发布主体或业务领域前缀（不使用 `government_*`、`engineering_*` 这类命名）。
2. 0.x 阶段**只增不删**；新增取值走 `MINOR`，删除或改名走 `MAJOR`；仅调整展示顺序走 `PATCH`。**数量不是规范不变量**，本期为 12 个。
3. `other` 是**显式声明**，不是缺省值；调用方拿不准时必须自己判断，不允许「不填就 other」。
4. 报告类的二级对象是受控细分：同一文档只能落在 `work_report` / `project_report` / `assessment_report` 之一，不得双标。
5. `work_report` 与 `assessment_report`：前者陈述「做了什么、进展如何」，后者给出「对某个对象鉴定/检验/审计/评估/研究的结论」。
6. `work_report` 与 `official_correspondence`：报告是法定公文文种之一，但本项目将其单列；其余文种归 `official_correspondence`。企业按公文格式行文的通知、函同样归 `official_correspondence`。
7. `project_report` 与 `assessment_report`：前者是工程/项目的过程与阶段文件，后者是对工程/项目/产品等对象的结论文书；同一文档按主体目的择一。
8. `project_report` 与 `development_plan`：规划是对区域/组织未来目标的公共或组织安排；项目建议书、可研报告是具体项目的前期文件，归 `project_report`。
9. `official_correspondence` 与 `internal_policy`：对外行文归公文；只在本单位内部生效、不对外行文的归内部制度。
10. `regulation` 与 `standard`：法律规范由立法/行政机关制定，技术规范由标准/认证机构制定；强制性标准仍归 `standard`，不因强制属性归 `regulation`。
11. `standard` 与 `operational_manual`：标准规定「要求/准则」，手册规定「怎么做」；检验规程属标准，设备操作步骤属手册。
12. `internal_policy` 与 `operational_manual`：制度是规则文本（应当/不得/责任），手册是操作指导（步骤/参数/图示）。
13. `contract` 与 `official_correspondence`：产生双方/多方权利义务的归合同；单方行文、不产生合同义务的归公文。
14. `litigation_document` 与 `assessment_report`：诉讼文书是程序性文书；鉴定意见书、评估报告是结论文书，归 `assessment_report`。

**旧名迁移**（仅文档层，尚未进契约）：

| 旧名 | 新名 |
| --- | --- |
| `government_report` | `work_report` |
| `engineering_project_report` | `project_report` |
| `government_plan` | `development_plan` |
| `official_document` | `official_correspondence` |
| `judicial_document` | `litigation_document` |
| `law_regulation` | `regulation` |
| `technical_standard` | `standard` |

## 2.1 已否决的 14 类方案

曾从「知识库建库单元」视角提出新增 `tabular_record`、`qa_pair`，并从 `report` 拆出 `appraisal_report`。该方案已否决：

- `tabular_record` 是版式/结构差异，应由 `traits.dense_table` 承载；
- `qa_pair` 是内容组织方式，不是文书体裁；
- `appraisal_report` 只是把 `assessment_report` 的语义显性化，不需要再拆一个与 `work_report` / `project_report` 重叠的类别。

若后续确需表达表格/问答形态，单独立 `contentForm` 维度或扩 `traits`，不塞进 `documentCategory`。

## 2.2 新增提议：用途维度 `usagePurpose`

类别描述「内容形态」，用途描述「怎么消费」，二者正交。同一份法规，检索要按条切，生成要给完整章节，训练要保留长文连贯性，不能用同一套块参数。

建议新增独立字段 `usagePurpose`，封闭枚举三值：

| 枚举值 | 定义 | 对切片的硬性要求 | 典型产物 |
| --- | --- | --- | --- |
| `rag_retrieval` | 供检索召回 | 块小、边界准、可独立命中；父子块模式（子召回、父补上下文） | 子块 + 父块配对 |
| `rag_generation` | 供推理时喂给模型生成答案 | 块**自包含**，不依赖 `previousChunkId`/`nextChunkId`；标题路径随块输出；父块必须完整 | 带 heading 路径的块 |
| `model_training` | 供微调或继续预训练 | 块**语义完整且足够长**（整章/整节/整篇），严格近重复去重，保留来源、授权与文档边界 | 长文语料 + 元数据 |

约束建议：

1. `usagePurpose` 与 `documentCategory` 相互独立，**不得互相推导**：不能因为类别是法规就默认用途是检索。
2. 一个知识库可同时声明多个用途；同一文档按不同用途可产出不同切片集，但 `chunkId` 必须能区分用途（建议策略名带用途标记）。
3. `model_training` 与 `rag_generation` 的验收口径不同：前者看语料连贯性、去重率、授权合规；后者看引用完整率与答案忠实度；后者与检索 recall 也不能混用同一阈值。三者由 Bench 分别标定，本仓只提供判定契约。
4. `rag_generation` 的「自包含」是硬约束：块若必须依赖前后块才能读懂，属质检缺陷，应进 Judge 规则候选（暂不新增编号，待评审）。
5. `model_training` 涉及版权与个人信息合规，属调用方责任；本仓不提供授权判断，只要求在产物中保留来源字段以便追溯。

> 本条为**新增提议**，尚未冻结；若认可，按 `MINOR` 落地（新增可选字段或必填字段需另行裁定）。

## 3. 决策项 B：特征产出方与职责边界

| 角色 | 职责 | 不做的事 |
| --- | --- | --- |
| 调用方 / 执行器（AEC.Chat 等） | 文档解析、结构识别、产出 `documentCategory` 与 `traits[]` | 不实现判定规则 |
| 本仓 Spec（`TemplateResolver`） | 消费 `traits` 与类别，按模板决策表选型；不解析文档 | 不产出特征、不补全缺失特征 |
| 本仓 Judge | 校验切片结果并出 `JudgeReport` | 不做选型、不解析文档、不做 NLP/LLM 推断 |
| 本仓 Bench（独立仓） | 用同一模板与契约做策略评测、回填分位数 | 不产出判定结论 |

约束建议：

1. `traits` 为封闭枚举，沿用现行 5 个：`article_numbering`、`section_numbering`、`weak_structure`、`dense_table`、`pdf_no_structure`；扩枚举走 `MINOR`。
2. 执行器**无法识别**某个特征时，必须在数组中**省略**该 trait，不得猜测、不得伪造。
3. `traits` 全为空数组是合法输入，语义为「未识别到任何结构特征」，由模板 fallback 兜底。
4. 本仓不因类别或特征缺失而自行推断；如需推断能力，只能放在执行器或旁路服务，不进本仓。

### 3.1 特征契约（建议冻结口径）

本仓规范的是**特征的词汇表与语义**，不是识别方法。

| 项 | 建议 | 说明 |
| --- | --- | --- |
| `traits` 取值 | 封闭 5 值，沿用现行 | 扩枚举走 `MINOR` |
| `traits` 空数组 | 合法 | 表示「未声明结构特征」，不等于「未知」，不触发报错，由 fallback 兜底 |
| `traits` 无法识别某项 | 省略该值 | 不得猜测、不得伪造 |
| `documentCategory` 取值 | 封闭枚举，按 C-01 冻结 | 枚举外值一律拒绝，不做最接近匹配 |
| 选型请求中的类别 | **必填且非空** | 空数组视为未提供类别，拒绝，不得静默走 fallback |
| `traits` 与 `structureHints` | 互不校验 | `traits` 是产出方结论，`structureHints` 是原始提示；不一致不报错，Judge 不据此推断 |
| 传递位置 | 本期仍只在 `/templates/resolve` 请求 | `DocumentFeature` 目前无 `documentCategory` / `traits`；是否随文档全程流转见 §5 第 6 问 |

错误处理建议（与现行 OpenAPI 对齐，统一用 `400`，不新增 `422`）：

| 情形 | 处理 |
| --- | --- |
| `documentCategories` 为空数组 | `400`，错误码建议 `document_category_required` |
| `documentCategories` 含枚举外值 | `400`，错误码建议 `document_category_unknown`，并列出合法枚举 |
| `traits` 含枚举外值 | `400`，错误码建议 `trait_unknown` |
| `traits` 为空 | 合法，继续选型 |

> 原草案写 `422`，与现行 `contract/openapi.yaml` 只有 `400` 的事实不一致，故改为 `400`；若坚持 `422`，属新增响应码，需单独走契约变更。

## 4. 决策项 C：未命中处理

分三种情形，互不替代：

| 情形 | 建议处理 | 理由 |
| --- | --- | --- |
| `documentCategories` 为空数组 | 宿主返回 `400`，错误码 `document_category_required` | 类别决定模板选择与报表口径，静默补值会污染评测分组 |
| `documentCategories` 为枚举外字符串 | 宿主返回 `400`，错误码 `document_category_unknown`，列出合法枚举 | 契约外值属于调用方错误，不能由本仓猜测最接近类别 |
| `traits` 含枚举外值 | 宿主返回 `400`，错误码 `trait_unknown` | `traits` 是封闭枚举，扩值只能走契约变更 |
| `traits` 未命中任何 `decision.rules` | **强制 smart fallback**（现行已实现） | 判定单原始口径：不允许无决策结果；兜底必须可执行、可复现 |
| `documentCategories` 与 `appliesTo` 无交集 | **模板集形态返回 `400` `no_applicable_template`**；单模板形态仍由部署侧选定 | 0.8.0（C-18）起 `TemplateResolver` 已按 `appliesTo` 做类别过滤，旧描述已过时 |

需要明确的一点：`documentCategory` 必填与 `traits` 兜底是**两条独立防线**。前者保证输入合法，后者保证有决策结果；不能用 fallback 掩盖类别缺失或类别非法。
