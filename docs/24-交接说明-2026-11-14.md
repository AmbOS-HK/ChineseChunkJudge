## 1. 这个仓是什么，不是什么

- 是 **判定契约仓**：定义「切片结果是否符合契约」，并提供一个 C# 参考实现。权威文件是 `contract/rules.md` + `contract/openapi.yaml` + `contract/schema/*.json`。
- **不是**切片算法仓：不内置解析器、不内置切分算法（见 `rules.md` §1.1）。执行器是外部插件。
- **不是**评测仓：策略优劣由另一个仓库 **ChunkJudgeBench** 横向评测，两仓独立并存，不存在替代关系。不要把评测逻辑塞进本仓。
- 本仓不接收 HTTP 宿主实现；`openapi.yaml` 是跨语言一致性契约，不代表仓内有服务端。

## 3. 三条铁律（违反任一条，改动一律退回）

1. **契约先行**：先改 `contract/`（顺序固定：`rules.md` → `schema/*.json` → `openapi.yaml`），再同步 `impl/`，最后改文档。禁止实现侧单独改字段或规则。
2. **基础规则不可变**（§8.4）：CCJ-001..021 不可删除、不可改编号、不可降级、不可改判定条件。要收紧只能**新增规则**，要放宽必须走 MAJOR 并在业主批准下进行（当前 0.x 阶段有「只增不删」冻结约定）。
3. **版本三处同值 + 一次只升一个位**（§12.1）：删字段/字段转必填/放宽条件/改语义/改规则级别 → MAJOR；新增字段（含可选）/新增基础规则/新增端点/收紧条件/新增枚举值 → MINOR；纯澄清与缺陷修复 → PATCH。同批次含多个性质时取最高位。三处任一漏改即视为缺陷。

## 8. 改一份契约的标准动作（照做即可）

1. 先读 `contract/rules.md` 对应章节，确认要改的是「正文」还是「规则表」还是「Schema」。
2. 判定版本位：按 §12.1 表逐条比，命中即停，写下结论（含理由）。
3. 按顺序改：`rules.md` → `schema/*.json` → `openapi.yaml`；三处版本同值。
4. 同步 `impl/csharp`：新增规则类一律实现 `IChunkRule`，注册进 `ChunkRuleIds` / `DefaultBaseRuleIds` / `CreateDefaultRules()`；规则不得重复报同一缺陷（作用域互斥写进 §8.4）。
5. 补测试：每条新规则至少 **触发 / 不触发** 两侧用例，并防止与既有规则双计。
6. 跑四条门禁 + `dotnet test`；`check_contract_bump.py --base origin/main` 必须 PASS。
7. 更新文档：`docs/` 新记录 + `README` 索引 + `docs/03` 计数；契约与实现放**同一个提交**（否则中间提交过不了版本门禁）。
8. 提交信息用 Conventional Commits，示例：`feat(contract): 0.10.0 契约收口，新增 CCJ-018..021`。

## 9. 交接边界

- 决策权在业主：涉及 MAJOR、放宽约束、新增端点、删除字段，必须先取得明确批准再动手。
- 本文不承诺任何未验证的能力：仓内没有 HTTP 宿主，因此「400/404 行为」只能靠契约文本与库内断言，不能声称端到端跑通。
- 若发现契约与实现不一致，按「先改契约再改实现」处理，并在 `docs/` 留证据；不要静默改实现迁就契约缺失。
