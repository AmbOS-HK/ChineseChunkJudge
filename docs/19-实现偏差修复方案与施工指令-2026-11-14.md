## 2. P1：结构父不再被覆盖，且让 CCJ-014 可达（I-01）

**契约依据**：`rules.md` §7.1 L203「`parentChunkId` 为旧名，**deprecated**，语义等同 `structuralParentChunkId`」、L207「调用方已显式指定时保留原值，不覆盖」、L209「`parentChunkId` 保留以兼容现有消费方」；`contract-chunk.json` L85 把 `parentChunkId` 列为 relations 的 required 字段（值可为 null）。

**已定方案（择 B）**：**只补空值、绝不覆盖非空值**。理由见 §11.5。

**现状**（`src/ChineseChunkJudge.Core/Builders/ChunkRelationBuilder.cs`）：

- L24 `ResolveParent(...)` 先取 `ParentChunkId`，再取 `StructuralParentChunkId`，再按 heading 推断；
- L32-33 把同一个结果**同时写进** `ParentChunkId` 和 `StructuralParentChunkId`，导致两个字段恒等，CCJ-014（L106-111 要求两者同时非空且不等）永远不触发。

**目标行为**：

| 输入 | 期望输出 |
| --- | --- |
| 两字段都显式给出且不同 | **各自保留原值** → 判定阶段 CCJ-014 报 warning |
| 只给 `parentChunkId` | `parentChunkId` 保留；`structuralParentChunkId` **补成同值** |
| 只给 `structuralParentChunkId` | `structuralParentChunkId` 保留；`parentChunkId` **补成同值** |
| 两者都为空 | 按 heading 推断一次，两个字段都写成推断结果（保持原语义） |
| `previousChunkId`/`nextChunkId` | 仍按 index 重算，行为不变 |

**改法**（只改 `Build` 与 `ResolveParent` 两处，其余不动）：

```csharp
// Build 循环体内，替换 L24-34 这一段
string? declaredParent = NullIfBlank(chunk.Relations.ParentChunkId);
string? declaredStructural = NullIfBlank(chunk.Relations.StructuralParentChunkId);

string? parent = declaredParent;
string? structural = declaredStructural;
if (parent is null && structural is null)
{
    parent = InferParent(ordered, i, chunk);
    structural = parent;
}
else
{
    parent ??= structural;   // 只填空值，不覆盖
    structural ??= parent;
}

result.Add(chunk with
{
    Relations = chunk.Relations with
    {
        PreviousChunkId = previous,
        NextChunkId = next,
        ParentChunkId = parent,
        StructuralParentChunkId = structural
    }
});
```

- 原 `ResolveParent` 改名为 `InferParent`，**删掉前两个 early-return 分支**（L43-51），只保留 heading 推断部分；签名不变。
- 新增私有辅助：

```csharp
private static string? NullIfBlank(string? value) =>
    string.IsNullOrWhiteSpace(value) ? null : value;
```

- 类注释 L6-7 同步为：`按 index 顺序补 previous/next；结构父显式值保留，缺失的别名补成同值，两者都缺时按 heading 推断。`

**必加测试**（新建 `tests/ChineseChunkJudge.Core.Tests/ChunkRelationBuilderTests.cs`，5 项）：

1. `Build_PreservesExplicitParentAndStructural_WhenTheyDiffer`：`Parent=parentA#0`、`Structural=parentB#0` → 构建后两值原样（**不得被抹平**）。
2. `Build_FillsStructuralFromParent_WhenOnlyLegacyFieldDeclared`：只给 `Parent=parentA#0` → `StructuralParentChunkId=="parentA#0"`。
3. `Build_FillsLegacyParentFromStructural_WhenOnlyNewFieldDeclared`：只给 `Structural=parentB#0` → `ParentChunkId=="parentB#0"`。
4. `Build_InfersSameHeadingParentForBothFields_WhenNeitherDeclared`：3 块（heading L1 + 正文 + heading L2）→ 正文块两字段同为 `structure@600#0`（沿用既有推断语义）。
5. `JudgeContractChunks_ReachesCCJ014_WhenAliasesConflict`：经 `new ChunkJudgeService().JudgeContractChunks(...)`（不是直接调 `ChunkValidator`）喂一个 `Parent=parentA#0`、`Structural=parentB#0` 的切片 → `Issues` 含 `CCJ-014` 且 `Severity=Warning`。

**回归风险**：既有 `ChunkValidatorTests.RelationBuilder_LinksNeighboursAndHeadingParent`（L267-286）只断言推断路径，改后不变，不得修改它。若它变红，说明推断路径被改坏，回退重做而不是改断言。

## 3. P2：`CCJ-015` 页码容错收窄（I-02）

**契约依据**：§8.5 L308「页码容错：句读 + 可选空白 + 1..4 位纯数字」。

**现状**：`RuleEngine/HardCutRule.cs` L17-19 `PageNumberEnding = @"[。！？；…\.!\?;][”’）】》]?\s*\d{1,4}$"`，在句读与数字之间多允许了一个闭合符，导致结尾 `。】123` 被判为"页码容错"而豁免。

**改法**：只改这一条正则，去掉 `[”’）】》]?`：

```csharp
private static readonly Regex PageNumberEnding = new(
    @"[。！？；…\.!\?;]\s*\d{1,4}$",
    RegexOptions.Compiled | RegexOptions.CultureInvariant);
```

`TerminalPunctuation`（L13-15）保持不变——它按契约允许"句读 + 闭合符"收尾，是正常句读判定。

**必加测试**（追加到既有的 `RuleTemplateAndHardCutTests.cs`，2 项）：

1. `IsHardCut_TreatsClosingBracketBetweenPunctuationAndPageNumber_AsHardCut`：`IsHardCut("甲乙丙丁戊。】123", 10)` → `true`。
2. `IsHardCut_KeepsPageNumberTolerance`：`IsHardCut("甲乙丙丁戊。 123", 10)` → `false`；`IsHardCut("甲乙丙丁戊。123", 9)` → `false`（句读紧邻数字仍豁免）。

该文件既有的 `ExactSizeWithPageNumberEnding_PassesByTolerance`（约 L239，文本 `。 123`）新正则下仍豁免，**不得动**；它变红说明正则改错。

**注意**：`IsHardCut` 的 `chunkSize` 参数语义是"恰好等于"（L68），测试里的第二参必须等于文本码位数，否则一律 `false`，测不出东西。

## 5. P4：`traits` 封闭枚举校验（I-04）

**契约依据**：§13.1 L426「`traits` 封闭枚举（`article_numbering`/`section_numbering`/`weak_structure`/`dense_table`/`pdf_no_structure`），扩枚举走次版本」。

**现状**：`Builders/TemplateResolver.cs` `ValidateRule`（L178-211）校 `chunkMode`/`pattern`/`chunkSize`，不校 `traits`；`ValidateTemplate`（L151-166）不校 `appliesTo.traits`。未知 trait 被接受（探针 C5 实测走 fallback、不抛错）。

**改法**（`TemplateResolver.cs` 内）：

```csharp
private static readonly IReadOnlySet<string> KnownTraits = new HashSet<string>(StringComparer.Ordinal)
{
    ChunkTraits.ArticleNumbering,
    ChunkTraits.SectionNumbering,
    ChunkTraits.WeakStructure,
    ChunkTraits.DenseTable,
    ChunkTraits.PdfNoStructure
};
```

- `ValidateTemplate` 内、`ValidateFallback` 调用之后加一行：`ValidateTraits(template.AppliesTo.Traits, "appliesTo");`
- `ValidateRule` 内、`ValidateChunkSize` 之后加一行：`ValidateTraits(rule.Traits, $"decision.rules[{index}]");`
- 新增方法：

```csharp
private static void ValidateTraits(IReadOnlyList<string>? traits, string location)
{
    if (traits is null)
    {
        return;
    }

    foreach (var trait in traits)
    {
        if (!KnownTraits.Contains(trait))
        {
            throw new ArgumentException(
                $"{location}.traits 含未定义取值 {trait}；traits 为封闭枚举，扩枚举须走契约次版本。");
        }
    }
}
```

**必加测试**（追加到既有的 `RuleTemplateAndHardCutTests.cs`，3 项）：

1. `Resolve_RejectsUnknownTrait_InDecisionRule`：`decision.rules[0].Traits=["not_a_real_trait"]` → `Assert.Throws<ArgumentException>`。
2. `Resolve_RejectsUnknownTrait_InAppliesTo`：`appliesTo.Traits=["not_a_real_trait"]` → `Assert.Throws<ArgumentException>`。
3. `Resolve_AcceptsAllFiveContractTraits`：五个合法 trait 各建一个模板 → 均能 `Resolve` 不抛错。

**明确不做**：不校验 `appliesTo.documentCategories` 是否非空（Schema 侧约束，属另一议题，别顺手加）。

## 7. P6：`/rules` 的库侧载体（I-06）

**契约依据**：`openapi.yaml` `GET /rules` → `RuleManifest{contractVersion, rules[]}`；`RuleDescriptor` 恰好 4 字段（`ruleId`/`description`/`severity`/`isBaseRule`），`additionalProperties: false`，`ruleId` pattern 允许 `CCJ-X###`。

**现状**：全仓只有 `ContractConstants.ContractVersion`（`Models/ChunkContract.cs` L18），无 `RuleManifest`/`RuleDescriptor` 类型、无组装方法。

**改法**：

1. 新建 `src/ChineseChunkJudge.Core/Models/RuleManifestContract.cs`：

```csharp
namespace ChineseChunkJudge.Core.Models;

/// <summary>规则清单中的单条规则描述（对应 openapi RuleDescriptor，恰好四个字段）。</summary>
public sealed record RuleDescriptor
{
    public required string RuleId { get; init; }

    public required string Description { get; init; }

    public required ChunkIssueSeverity Severity { get; init; }

    public required bool IsBaseRule { get; init; }
}

/// <summary>GET /rules 的响应体：契约版本 + 生效规则清单（含扩展规则）。</summary>
public sealed record RuleManifest
{
    public required string ContractVersion { get; init; }

    public required IReadOnlyList<RuleDescriptor> Rules { get; init; }
}
```

2. `ChunkJudgeService.cs` 加一个公开方法（放在 `RuleEngine` 属性 L27 之后）：

```csharp
/// <summary>规则清单：契约版本 + 当前引擎内全部生效规则（含扩展规则）。</summary>
public RuleManifest GetRuleManifest() => new()
{
    ContractVersion = ContractConstants.ContractVersion,
    Rules = RuleEngine.Rules
        .Select(r => new RuleDescriptor
        {
            RuleId = r.RuleId,
            Description = r.Description,
            Severity = r.Severity,
            IsBaseRule = r.IsBaseRule
        })
        .ToList()
};
```

**不要**复用 `AppliedRule`：它与 `RuleDescriptor` 字段相同但语义不同，将来任一侧加字段会把另一侧带出 Schema 违规（`additionalProperties: false`）。

**必加测试**（`JsonContractTests.cs` 内追加 2 项，沿用该文件已有的序列化校验风格）：

1. `RuleManifest_ListsAllSeventeenBaseRules_AndContractVersion`：`GetRuleManifest()` → `ContractVersion=="0.9.0"`、`Rules.Count==17`、17 个 `ruleId` 全部 `IsBaseRule==true`、且与 `ChunkRuleEngine.DefaultBaseRuleIds` 集合相等。
2. `RuleManifest_SerializesWithExactlyFourDescriptorFields`：序列化后 `rules[0]` 的键集合恰为 `ruleId/description/severity/isBaseRule`；`contractVersion` 为字符串。

**边界**：`Register` 注册的扩展规则必须出现在清单里（用 `Rules` 而非 `CreateDefaultRules()`）；本项不含 HTTP 路由/宿主。

### 11.5 P1 两个选项的对比（已定 B）

| 维度 | A：只保留显式值，缺的留 null | B：只补空值，缺的补成同值 |
| --- | --- | --- |
| 契约依据 | §7.1 L207「保留原值，不覆盖」字面满足 | 同样满足（只填空值，不覆盖已有值）；另合 L203「语义等同」、L209「保留以兼容现有消费方」 |
| Schema | 合规（`structuralParentChunkId` 非 required；`parentChunkId` 存在但可为 null） | 合规；「只给新名」时也能输出 Schema 列为 required 的 `parentChunkId` 且非 null |
| CCJ-014 | 冲突场景可达（两值原样保留） | 冲突场景同样可达（补值只发生在空值，不抹平两值不同） |
| 与修复前相比 | **会改**：单字段输入的一个别名由「有值」变 null | **不改**：单字段输入输出与修复前一致；只改冲突场景（由抹平变保留） |
| 老消费方（读 deprecated `parentChunkId`） | 只给新名时读不到父 → 丢父，须加回退 | 仍读到父 → 无需适配 |
| 新消费方（读 `structuralParentChunkId`） | 只给旧名时读到 null → 须加回退 | 读到父 |
| 迁移导向（1.0.0 移除 `parentChunkId`） | 逼迫消费方写「先新后旧」回退 | 继续容忍旧字段，迁移压力靠文档与弃用统计承担 |
| 数据忠实度 | 输出与输入严格一一对应 | 输出含实现补出的等价字段（与 `Normalize` 补 `chunkId`/`charCount` 同性质） |
| 能否看出「调用方仍用旧字段」 | 能（structural 为 null） | 不能，需另加统计 |

**结论：取 B。** 三条理由：

1. §7.1 L209 明写 `parentChunkId` 保留是「以兼容现有消费方」；A 在「只给新名」时把这个兼容字段留空，恰好打掉它存在的目的。
2. `contract-chunk.json` L85 把 `parentChunkId` 列为 relations 的 required；B 保证它始终有值（除两侧都空且无推断的情况）。
3. 爆炸半径：B 只改「两值冲突」一种输入，A 会改动所有单字段输入。

**代价与缓解**：B 抹掉了「调用方仍在用旧字段」这个信号。若 1.0.0 前要推迁移，不靠输出形态暗示，改为统计「由别名补值的次数」（日志或报告 `detail`），列入 0.10.0 之后的待办。

**一处更正**：上一轮我说「补成同值会让 CCJ-014 重新不可达」——那只对**无条件抹平**成立；按 B 的「只补空值」，两值都为非空且不同时不会补，CCJ-014 依旧可达。原文按 B 修正。
