## 2. 阻断级问题（K-01..K-05）

### K-01 关系指针"必填"与参考实现序列化口径冲突（已实证）

- 契约：`contract-chunk.json` 的 `relations` 把 `previousChunkId`、`nextChunkId`、`parentChunkId` 列为 `required`（`schema/contract-chunk.json` L85）。
- 实现：`ChunkJson.CreateOptions` 设置 `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull`（`Models/ChunkContract.cs` L330），null 成员整字段省略。
- 实测：首块输出 `"relations": { "nextChunkId": "structure@1200#1" }`，缺 `previousChunkId` 与 `parentChunkId`；末块缺 `nextChunkId` 与 `parentChunkId`。共 4 处违反 `required`。
- 影响：`openapi.yaml` 的 `POST /chunks/normalize` 响应规定为 `array<contract-chunk>`。任何以本库为内核的宿主，只要诚实序列化，返回体就不符合自己的 Schema；跨语言实现若严格按 Schema 校验，会判 C# 产物非法。这是"契约与首个参考实现不一致"的直接证据。
- 修法（PATCH 级，不动契约）：让序列化对 `relations` 的五个指针**显式输出 null**（`[JsonIgnore(Condition = Never)]` 或专用 DTO），保留 `headingPath` 等可选字段的省略行为（该省略已被 `HeadingPathTests` 锁定，且 Schema 未将其列入 required）。
- 不建议的修法：把 `required` 改成可选。那属于放宽判定条件，按 §12.1 是 `MAJOR`，且会丢失"关系字段必须显式给出（null 表示无）"这一可判定语义。

### K-02 弃用字段必填、正式字段可选（结构倒置）

- 契约：`relations.required` 含 `parentChunkId`（**deprecated**，1.0.0 移除），而接替它的 `structuralParentChunkId` 不在 required（`contract-chunk.json` L85、L97）。
- 影响：新实现被迫输出一个它本不该再产出的弃用字段；`CCJ-014` 只在两者同现时触发，判定能力被这一倒置架空；`docs/02` §4 明确"1.0.0 删除 `parentChunkId`、`structuralParentChunkId` 转必填"，即当前状态与既定路线相反。
- 修法：**本轮不改**，作为 1.0.0 的既定破坏性变更一并翻转（已在 `docs/02` 台账）。若希望 0.x 期间即消除矛盾，等价方案是把 `required` 改为 `structuralParentChunkId` 并把 `parentChunkId` 移出 required——属收紧 + 放宽同时发生，须明示走 `MAJOR`，不建议在 0.x 做。

### K-03 策略名里的 `targetSize` 区间无任何约束

- 契约：§5.1 规定 `targetSize` 取值 `1..1500`，但给出的"完整校验正则"`^[a-z][a-z0-9_-]*@[1-9][0-9]*$`（L121）不含上限；`CCJ-002` 只校验这条正则；`CCJ-007` 只校验 `options.targetSize`，不校验切片自带的 `strategy` 字符串。
- 后果：`structure@2000#0` 这种切片，`strategy` 过 Schema、过 CCJ-002、过 CCJ-017，无处可拦；`strategy` 与 `options` 的 `targetSize` 是否必须一致也没有规则。
- 修法：`MINOR`。两条都要：Schema 侧给 `strategy` 增加可校验的区间表达（拆出 `type`/`targetSize` 模式或加 `if-then`），规则侧新增一条基础规则校验"策略名后缀 ∈ 1..1500 且与 options 一致"。二者都属收紧。

### K-04 `maxChunkSize` 的"硬上限"没有判定规则

- 契约：§5.2 称 `maxChunkSize` 为"单块硬上限"，默认 1500，"不得大于 1500，即不得放宽上限"（L132）。
- 实现：`CCJ-004` 只比较 `charCount > 1500`（`ChunkRuleEngine.cs` L206）；`CCJ-007` 只校验该选项自身的取值范围与 `maxChunkSize >= targetSize`。**没有任何规则把切片长度与 `maxChunkSize` 比一比**。
- 后果：`targetSize=1200`、`maxChunkSize=600` 时，一条 1100 字的切片既不触发 CCJ-004，也无其他告警；"硬上限"在契约里是一句无判定的形容词。
- 修法：`MINOR`，新增基础规则（`CCJ-018`）判定 `charCount > options.maxChunkSize`（warning 或 error 需定级）。若不打算判定，则应把 §5.2 的"硬上限"改为"配置项（仅用于执行器）"，属 `PATCH` 级措辞澄清，但必须二选一。

### K-05 §4.1 "与文档一致"的五字段快照无规则

- 契约：§4.1 规定"每份 `ContractChunk` 都必须携带与文档一致的五字段快照"（L95）；`CCJ-001` 的触发条件只是"任一字段缺失或为空"（L277）。
- 实现：`MetadataCompletenessRule` 只调 `IsFieldMissing`，不做与 `DocumentFeature.metadata` 的等值比较（`ChunkRuleEngine.cs` L84-90）。
- 后果：切片携带一份完整但**与文档不同**的元信息（例如错 `title`、错 `createTime`）可判通过；下游按切片元信息回指文档时会张冠李戴。父块（`ContextParentChunk`）同样无一致性校验。
- 修法：`MINOR`，新增基础规则校验子块/父块 `metadata` 与 `DocumentFeature.metadata` 逐字段相等（`createTime` 需定比较口径：字符串相等还是时间相等）。注意 §8.4 禁止改 `CCJ-001` 的判定条件，只能新增编号。
