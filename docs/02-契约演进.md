### 3.5 C-10 / C-11 立项依据（2026-11-13）

**源头**：AEC.Chat《切片判定单 V1.0》主干是「文档 → 结构特征 → 切分方式 + chunkSize → 恰长硬切验证 → 回归」的决策链。现行 0.2.0 只覆盖「验证 + 记录」环节与双库扩展，决策链本体未进契约。项目定位为 **Spec（规则模板）+ Judge（质检判定）双判定**，评测仍归 ChunkJudgeBench，不并入本仓。

**判定单要素映射**：

| 判定单要素 | 落点 |
| --- | --- |
| 文档类别（法规制度 / 规划文本） | 模板 `appliesTo`，依赖 C-01/C-02 |
| 结构特征（条章 / （一）分节 / 弱结构 / 密集指标表 / PDF 无结构） | 模板 `appliesTo` 的结构谓词 |
| 切分方式（条正则 / （一）正则 / 智能切分 / page） | `chunkMode`：`regex` / `smart` / `page` |
| 正则与禁忌（禁 `^` 多行锚、禁 h3 切分） | `pattern` + 约束表达（形式待定） |
| chunkSize 1000 / 1200 / 1500 | 模板参数，引用而非复制 `ChunkStrategyOptions` |
| 恰长硬切 = 0、页码容错 | C-11 新校验规则 |
| 27 问回归 | ChunkJudgeBench，不进本仓 |
| 库名（aec-law / aec-plans） | **不进通用契约**，属 AEC.Chat 部署侧配置 |

**模板字段草案（未冻结）**：`templateId` / `version` / `name`；`appliesTo`（文档类别 + 结构特征谓词）；`chunkMode`（`regex` / `smart` / `page`，`regex` 时含 `pattern` 与禁忌约束）；`chunkSize`；`parentChild` 引用；`validation`（恰长硬切 = 0、是否触发回归）；`decision` 有序规则表，先匹配先生效。

**与既有条目的关系**：C-10 的 `decision` 即 C-04「分流」的模板化承载，落地时 C-04/C-05 应并入 C-10 评审，避免两套分流定义并存。

### 3.6 C-10 模板规范（文档层冻结，0.3.0 实施依据；本节约束未进 `contract/`）

`ChunkRuleTemplate` 字段：

| 字段 | 类型 | 必填 | 约定 |
| --- | --- | --- | --- |
| `templateId` | string | 是 | `^[a-z][a-z0-9_-]*$` |
| `version` | string | 是 | 模板自身版本，与契约版本独立演进 |
| `name` | string | 是 | 展示名 |
| `appliesTo` | object | 是 | `documentCategories: string[]`（C-01 落地前为自由字符串，不把五分流写成契约枚举）+ `traits: enum[]` |
| `decision.rules` | array | 是 | 有序，**先匹配先生效**；每条 = `{ traits, chunkMode, pattern?, chunkSize, parentChild? }`，`traits` 全部满足才命中 |
| `decision.fallback` | object | 是 | **强制兜底**：`chunkMode=smart`，`chunkSize` 必填；未命中任何规则时必须落 fallback，不允许无模板结果（对应判定单「拿不准就智能切分」） |
| `validation` | object | 否 | `hardCutZero: boolean = true`；`acceptanceRef: string` 可选（如 27 问回归标识，执行归 Bench） |

`traits` 枚举（封闭集合，扩枚举走次版本）：`article_numbering`（第X条/章）、`section_numbering`（（一）（二）分节）、`weak_structure`、`dense_table`、`pdf_no_structure`。

`chunkMode` 与约束：

- `chunkMode` ∈ `regex` / `smart` / `page`；`regex` 时 `pattern` 必填，其余模式禁止携带 `pattern`；`page` 用于 PDF 无可靠结构。
- 正则禁忌用**枚举字段**表达，不用自由文本（否则机器无法校验）：`forbidLineStartAnchor: boolean = true`（禁 `^` 多行锚）、`forbidHeadingSplit: boolean = true`（禁 h3 标题切分）、`preserveSeparator: boolean = true`（保留分隔符，不丢标点）。
- `chunkSize`：integer，1..1500，与 `MAX_CHUNK_CHARS` 一致；智能切分为**软上限**，实测可超出，恰长判定见 §3.7。
- `parentChild` 引用 §5.3 配置，不复制字段。
- 库名（aec-law / aec-plans）不进模板，由部署侧把库映射到 `templateId`。

### 3.7 C-11 / CCJ-015 恰长硬切规范（文档层冻结，0.3.0 实施依据）

- **编号与级别**：CCJ-015，**error**（`passed=false`）。理由：判定单要求恰长硬切数必须为 0，属验收红线；部署侧展示降级不得改变契约语义（§8.4）。
- **判定对象**：`ContractChunk`（子块）。`page` 模式豁免；上下文父块不适用（父块仅受 CCJ-009 告警约束）。
- **判定条件（同时满足）**：
  1. `charCount` **恰好等于**当前生效 `chunkSize`；
  2. 切片结尾不属于允许结束集合。
- **允许结束集合**：中文句读 `。！？；…` 及英文 `.!?;`，含其闭合形式（结尾为 `” ’ ） 】 》` 等右闭合符且前一位为句读）。
- **页码容错**：结尾匹配「句读 + 可选空白 + 1..4 位纯数字」视为页码，不计硬切。
- **超限不判**：`charCount > chunkSize`（智能切分软上限）不走本规则，仍由 CCJ-004 处理；`charCount < chunkSize` 不判。
- **与 CCJ-005 的区别**：CCJ-005 校验文本与原文区间一致，CCJ-015 校验截断方式，二者独立、可同现。
- **summary**：0.3.0 新增 `hardCutChunkCount`，逐文档计数。
- **实施校准项（不属未决决策）**：允许结束集合与页码正则在实施时以 AEC.Chat `check_hardcut.sh` 的实际口径校准，若有出入回记本节，不改变「恰长 + 非句读结尾 = error」的判定结构。

### 3.1 C-06 设计理由与取舍（规划文档记录，不进契约正文）

**一句话**：兼顾检索精度与上下文完整性，解决“小切片搜得到但信息断、大切片上下文够但召回不准”的矛盾。

**收益（面向工程 / 司法鉴定 / 合同 / 规范类文档）**

1. **召回更准**：子块语义单一，向量不易被多个无关子话题稀释；R@5、MRR 类指标优于整块入向量。
2. **上下文不残缺**：细切常把条款拦腰截断、表格拆开、编号条文分离；父块把关联内容打包，命中子块后取父块，避免 LLM 断章取义。
   例：子块“检验误差不得大于 5%”，父块含本条 + 适用前提 + 测量条件 + 例外说明。
3. **灵活性在下游**：框架只输出配对，不强制；下游可开启双库、只用子块、或父块单独建索引做摘要 / 概览。
4. **评测友好**：检索命中基于子块（R@5、MRR），引文完整率 / 单元完整率基于父块，两套指标可分开统计，不必在“完整”与“召回”间取舍。

**短板（必须同步给接手方）**

1. 存储与向量计算量翻倍：一份文档产出两组切片，索引体积变大。
2. 链路复杂度上升：需维护父子 ID 映射。
3. 依赖正确的层级切分：父子配对本身切错，收益直接归零。

**评测口径映射（须与 ChunkJudgeBench 对齐）**

| 对象 | 承担的指标 |
| --- | --- |
| 子块 | 召回：R@5、MRR |
| 父块 | 上下文质量：引文完整率、单元完整率 |

### 3.2 规则冻结前的三处纠偏（2026-11-13）

1. **CCJ-006 不得改写**。现行 CCJ-006 是「相邻切片区间重叠 → warning」，§8.4 规定基础规则**不可改变判定条件**。「一个子块只能归属一个 contextParent」属于配对完整性，归入 **CCJ-008**，不写进 CCJ-006；同理「放开 CCJ-006 允许多归属」也不成立，多归属与否由 CCJ-008 判定。
2. **「不重叠 + 全文划分覆盖」隐含了切分顺序**：先按结构单元划分父块、再由父块切子块，否则「父块拼接＝原文」对任意切分器不成立。该流程约束须写进契约的数据流描述，但实现仍归外部执行器（不违反 §1.1）。同时，全文覆盖会强迫为封面、目录、空白区等非条款内容也生成父块，是否接受见 §5 第 18 条。
3. **跨父块引用 ID 是新增字段，不是零成本措辞**。`relatedContextParentIds` 需要 schema 承载，且必须回答：ID 是否必须可解析、能否自引用、是否允许成环（A→B→A）。未定之前不得写进对外文案。

### 3.3 「上限」措辞统一

CCJ-009 明确为**告警、不阻塞**，与 CCJ-004 同级。因此 `parentMaxChars` 应称「长度**告警阈值**配置项」，不称「上限」。现行 §8.2 把 `MAX_CHUNK_CHARS=1500` 称为「硬上限」但 CCJ-004 为 warning，属同型措辞矛盾，随 0.2.0 一并修正为「阈值」表述，不改变任何判定行为。

### 3.4 两条必须写进契约的推论

1. **§5-14「不封顶」是有意放宽，须如实记录**：父块长度此后只受样本统计与 CCJ-009 告警约束，契约不再保证父块长度可预期。收益是不卡死长条款组；代价是下游无法依赖契约推断父块大小，部署侧需自行加上限。这条与「作用域拆分 ≠ 豁免」的论证强度有关：现在父块侧只有告警，没有硬约束，论证应表述为「两级独立告警」，而非「两级独立上限」。
2. **双库模式下子块天然不重叠**：父块互不重叠（CCJ-010）+ 全文划分 + 子块区间 ⊆ 父块区间（CCJ-012），可推出同一文档内子块区间互不重叠。因此双库模式下 CCJ-006 应恒不触发；一旦触发，说明上游未遵守「先父后子」的数据流，属流程违规而非普通告警。此推论写进 §8.3 注释，不新增规则。
